# A. 数据库

## A1. 总览

原则：

1. 行程内容全部是数据库里的行，前端只负责渲染。代码里不出现任何城市、日期、币种、航班号。
2. 每个行程自带时区（`trips.timezone`）、汇总币种（`home_currency`）、当地币种（`local_currency`）。“今天是第几天”、汇率、天气都从这些字段推出来。
3. 一个事实只存一处：坐标只在 `places`；“已订/待确认/已付”只在 `bookings`；地图路线由当天条目按顺序连接地点得到；预算由条目的 `cost_estimate` 汇总。
4. 两个人一起改的内容直接改行（按行“后写者胜”），不再有每人一份的覆盖层。
5. 只有行程成员登录后才能读；未登录（anon）什么都读不到。

表一览：

| 表 | 用途 | 成员可读 | 谁能写 | 进实时 |
|---|---|---|---|---|
| `trips` | 行程 | 是 | owner/editor 改；owner 删；新建走 `create_trip()` | 是 |
| `trip_members` | 成员和角色 | 是 | 加入走 RPC；owner 改角色/移除；自己改展示名或退出 | 是 |
| `trip_invites` | 邀请码（只存哈希） | owner/editor | 只能走 RPC | 否 |
| `segments` | 分段（城市/区域） | 是 | owner/editor | 是 |
| `places` | 地点、想去清单 | 是 | owner/editor | 是 |
| `bookings` | 预订 | 是 | owner/editor | 是 |
| `days` | 每一天 | 是 | owner/editor | 是 |
| `items` | 时间轴条目 | 是 | owner/editor | 是 |
| `contacts` | 联系人 | 是 | owner/editor | 是 |
| `todos` | 待确认/打包/待办/要买 | 是 | owner/editor | 是 |
| `tips` | 防坑、消息模板、常用语、实用信息 | 是 | owner/editor | 是 |
| `journal_entries` | 日记（每天每人一篇） | 是 | 每个成员只能写自己的 | 是 |
| `reviews` | 地点评级（每人每地点一条） | 是 | 每个成员只能写自己的 | 是 |
| `expenses` | 记账（旧表补字段） | 是 | owner/editor | 是 |
| `trip_user_state` | 旧版覆盖层（台湾），保留待迁移 | 是 | editor 只能写自己的行 | 否 |
| `checkins` | 旧版打卡（台湾），保留 | 是 | 成员只能写自己的 | 否 |

关系（箭头指向被引用的表；除 `trip_members` 外所有内容表都带 `trip_id → trips`，图里省略）：

```
trips ─┬─ trip_members ── auth.users
       ├─ trip_invites
       ├─ segments
       ├─ places ───────────→ segments
       ├─ bookings ─────────→ places
       ├─ days ─────────────→ segments, bookings(stay_booking_id 当晚住处)
       ├─ items ────────────→ days, places, bookings, items(parent_item_id 备选方案)
       ├─ contacts ─────────→ bookings, places
       ├─ todos ────────────→ days, bookings, items
       ├─ tips ─────────────→ segments, days, places, bookings
       ├─ journal_entries ──→ days（删天会连带删日记）
       ├─ reviews ──────────→ places（删地点会连带删评级）, items
       └─ expenses ─────────→ items, bookings
```

表内引用都是 `(trip_id, xxx_id)` 组合外键，只能引用同一个行程里的行。被引用的行删除时：`journal_entries`、`reviews`、备选条目（`items.parent_item_id`）跟着删，其余引用字段置空（例如删掉一天，当天的条目进入备选池）。删除整个行程会删除它的所有数据。

## A2. 通用约定

### 系统列（每张内容表都有）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键。导入的数据由 key 生成（见 B3.1）；前端新建的行用随机 uuid（`crypto.randomUUID()` 或数据库默认值） |
| `trip_id` | text | 所属行程 |
| `created_at` | timestamptz | 新建时间，更新时由触发器锁定不变 |
| `updated_at` | timestamptz | 每次更新由触发器设为 `now()` |
| `created_by` | uuid | 新建者。登录用户写入时触发器强制设为本人；导入脚本写入时为空 |
| `updated_by` | uuid | 最后修改者，登录用户更新时由触发器设置 |
| `extra` | jsonb 对象 | 暂时没有专门字段的信息放这里，默认 `{}` |

`journal_entries`、`reviews` 另有 `user_id`（作者，必填，默认当前用户）。

### 时间、时区

| 类型 | 写法 | 含义 |
|---|---|---|
| `date` | `"2027-01-10"` | 当地日期 |
| `time` | `"15:30"` | 当地钟点，24 小时制。按该天所属分段的 `segments.timezone` 理解，分段没写就按 `trips.timezone` |
| `timestamptz` | `"2027-01-10T10:35:00+07:00"` | 一个确定的时刻，必须带偏移。显示时用旁边的 `*_tz` 字段或行程时区换算 |
| 时区 | `"Asia/Ho_Chi_Minh"` | IANA 时区名，数据库会校验 |

### 币种和金额

- 币种一律用 ISO 4217 三位大写代码：`HKD`、`CNY`、`TWD`、`VND`、`USD`。不再用 `NTD`、`RMB`（只在旧的 `expenses` 数据里出现，读 `currency_iso` 列即可）。
- 金额是数字（不加引号、不带千分位），按原币存。越南盾没有小数；港币、人民币最多两位小数。
- 换算成 `home_currency` 由前端做；记账时把当时用的汇率写进 `expenses.fx_rate`。

### 坐标

WGS84 十进制度，`lat` 纬度、`lng` 经度，两者要么都有要么都没有。没有坐标的地点不写坐标，前端退回到分段中心 `segments.center_lat/lng`，并标明“位置未知”。

### 排序

| 表 | 前端排序 |
|---|---|
| `segments` | `sort`，再按 `start_date` |
| `days` | `date` |
| `items` | 同一天内：`sort_key`，再按 `start_time`（空值在后），再按 `created_at`；`deleted_at` 不为空的不显示 |
| `bookings` | `start_at`（空值在后），再按 `sort` |
| `todos` | 按 `list` 分开；同一清单内 `sort`，再按 `created_at` |
| `contacts`、`tips` | `pinned`（仅 tips）在前，再按 `sort` |

拖拽调整顺序时，把 `sort_key` / `sort` 改成前后两条的中间值（`sort_key` 是 numeric，可以有小数）。

### 软删除

`items` 和 `expenses` 有 `deleted_at`：删除时写入时间，可以恢复；前端默认过滤掉。其余表直接删除行。

### 前端从数据推出来的东西（不入库）

| 内容 | 算法 |
|---|---|
| 第几天 | `days.date - trips.start_date + 1` |
| 行程阶段（未开始/进行中/已结束） | 用 `trips.timezone` 下的“今天”对比 `start_date`/`end_date`。`trips.status` 是手动状态，不代表阶段 |
| 当天地图路线 | 当天 `variant='primary'` 且未删除的条目，按排序取 `place_id` 的坐标连线 |
| 总路线 | 各 `segments` 按排序取中心点 |
| 预算 | 汇总 `items.cost_estimate`（见 B5），已订的用 `bookings.price_amount` |
| 天气 | 当晚住处（`days.stay_booking_id → bookings.place_id`）坐标，没有则用分段中心；加 `trips.timezone` 实时请求 |
| 那一刻人在哪个时区 | 去程航班（起飞地日期 ≤ 第一天的第一班 `kind='flight'`）落地（`end_at`）之前 = 它的 `start_tz`；回程航班（起飞地日期 ≥ 最后一天的最后一班）落地之后 = 它的 `end_tz`；其余 = `trips.timezone`（`selectors.presenceZone`）。「现在」的钟点、待办截止、记一笔的默认币种按它显示；和行程时区不同时注明「香港时间」 |
| 条目钟点 | 没标签的钟点 = 那一天的时区；`items.extra.local_time` 的写那边的钟点 + 地名；航班条目（开始 = 关联航班预订的起飞时刻）起飞按 `start_tz`、落地按 `end_tz`（`kit/item-clock.js`） |

## A3. 系统表（不通过行程 JSON 的普通数组导入）

### trips

字段见 B4.1。补充：

- `id` 是好记的 text，同时用在网址和存储路径里，建好后不能改。现有台湾行程是 `taiwan2026`，新行程如 `demo2026`。
- 旧字段 `description`、`cover_emoji` 保留（旧前端在用）。新前端读 `cover.emoji`，没有再读 `cover_emoji`。
- `owner_id` 只有 owner 能改（触发器拦截）。

### trip_members

| 列 | 类型 | 说明 |
|---|---|---|
| `trip_id` | text | 主键之一 |
| `user_id` | uuid | 主键之一 |
| `email` | text | 加入时记录的登录邮箱 |
| `role` | text | `owner` / `editor` / `viewer` |
| `display_name` | text | 界面显示名，可空 |
| `color` | text | `#RRGGBB`，头像/标记色，可空 |

角色：owner 拥有 editor 的全部权限，另外能改成员角色、移除成员、转让和删除行程。`trips.owner_id` 指向的成员也算 owner——台湾行程的创建者在表里是 `editor`（旧前端只认 `editor` 可编辑，所以不改旧数据），靠这条认定为 owner。

### trip_invites

| 列 | 说明 |
|---|---|
| `id` | uuid |
| `trip_id` | 行程 |
| `role` | 加入后的角色：`editor` / `viewer` |
| `code_hash` | 邀请码的 sha256（去掉连字符、转大写后计算）。数据库里不存明文码 |
| `invite_code` | 旧字段，新邀请为空 |

### trip_user_state（旧）

台湾版的“覆盖层”：每人每个 key 一行 jsonb（`completedItems`、`itemEdits`、`spotReviews`……）。保留不动，以后用一次性脚本按 `items.legacy_id` 合并进新表；新前端不读不写。

### checkins（旧）

台湾版打卡记录，保留不动。新前端用 `items.status='done'` 和 `journal_entries` / `reviews` 的照片代替。

## A4. 权限与 RPC

### 规则

- 所有策略只开放给 `authenticated` 角色；`anon` 对这些表没有任何表权限，也没有策略。
- 共享内容表（`segments`、`places`、`bookings`、`days`、`items`、`contacts`、`todos`、`tips`、`expenses`）：成员可读；owner/editor 可增删改。
- 个人内容表（`journal_entries`、`reviews`）：成员可读；任何成员只能增删改 `user_id` 是自己的行（viewer 也能写自己的日记和评级）。
- `trips`：成员可读；owner/editor 可改；owner 可删；不能直接 INSERT。
- `trip_members`：同行程成员互相可见；不能直接 INSERT；owner 能改任何人的角色、移除任何人；每个人能改自己的 `display_name`/`color`、能退出（删自己那行），但不能改自己的角色。
- `trip_invites`：owner/editor 能查看本行程的邀请；新建、使用、撤销只能走 RPC。

### RPC（`supabase.rpc(名字, 参数)`）

| 函数 | 参数 | 返回 | 谁能调 | 行为 |
|---|---|---|---|---|
| `create_trip` | `p_id text, p_title text, p_start_date date, p_end_date date, p_timezone text = 'Asia/Hong_Kong', p_home_currency text = 'HKD', p_local_currency text, p_subtitle text, p_cover jsonb = '{}'` | 行程 id | 登录用户 | 校验 id 格式和是否重复，写 `trips`（`owner_id` = 自己，`status='planning'`），同时写自己的 `owner` 成员行 |
| `create_invite` | `p_trip_id text, p_role text = 'editor', p_valid_hours int = 168, p_max_uses int = 1` | 明文码，如 `38S7-72Q9-FTCZ` | 该行程 owner/editor | 角色只能 `editor`/`viewer`；有效期 1–720 小时；次数 1–20。码 12 位，字母表 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（去掉 I O 0 1），只在这一次返回 |
| `redeem_invite` | `p_code text` | 行程 id | 登录用户 | 输入不分大小写，空格和连字符会被忽略。已经是该行程成员：直接返回，不消耗次数、不改角色。否则校验未撤销、未过期、次数未用完，加入并 `used_count + 1`。所有失败都报“邀请码无效或已过期” |
| `revoke_invite` | `p_invite_id uuid` | 无 | 该行程 owner/editor | 设置 `revoked_at` |
| `is_trip_member` / `is_trip_editor` / `is_trip_owner` | `check_trip_id text` | boolean | 登录用户 | 权限判断，RLS 内部使用，前端也可调 |
| `ping` | 无 | `'ok'` | 任何人（含 anon） | 保活用，不读任何表 |

前端示例：

```js
const { data: tripId, error } = await supabase.rpc('create_trip', {
  p_id: 'demo2026', p_title: '海岛 · 秋假',
  p_start_date: '2027-01-10', p_end_date: '2027-01-13',
  p_timezone: 'Asia/Ho_Chi_Minh', p_home_currency: 'HKD', p_local_currency: 'VND',
});
const { data: code } = await supabase.rpc('create_invite', { p_trip_id: tripId, p_role: 'editor' });
const { data: joined } = await supabase.rpc('redeem_invite', { p_code: code });
```

邀请链接建议用 `#/join/<码>`（放在 hash 里，不会进服务器日志）；页面读到后要求登录，再调 `redeem_invite`。

### 小程序桥接（wx_bridge，只给微信小程序的云函数用）

微信小程序不能直连 `supabase.co`（请求域名要备案），所以「豆豆小账本」的云函数 `trip` 用公开的 publishable key（`anon` 角色）调两个专用 RPC。迁移文件 `supabase/migrations/20261013090000_wx_bridge.sql`，排在 v2 主迁移之后执行；之后再执行 `20261014090000_wx_bridge_todo_edit.sql`（待办能改、能删：只替换 `private.wx_bridge_apply_op`、`private.wx_err_text`，新增 `private.wx_todo_refs`，不动表和对外入口）。两个文件都可重复执行（重跑前一个之后要再跑一次后一个，不然函数会退回只有 8 种改动的版本）；文件里只有结构，没有任何密钥、哈希或 user_id。

| 函数 | 参数 | 返回 | 谁能调 | 行为 |
|---|---|---|---|---|
| `wx_bridge_sync` | `p_key text, p_openid_hash text, p_trip_id text = null, p_hashes jsonb = '{}', p_ops jsonb = '[]'` | jsonb | 只有 `anon` | 认人 → 本事务内 `auth.uid()` = 这个人 → 先按顺序做完 `p_ops`（最多 50 条，每条一个子事务，逐条返回 `{op_id, ok, row}` / `{ok, gone}` / `{ok: false, code, error}`）→ 返回 `me`、`server_now`、`trips`（每趟带 `members`、`local_today`、`utc_offset_min`、`tz_offsets`）、`results`，以及 `p_trip_id` 这趟按表指纹的增量：`hashes`（13 张表各一个 md5）和 `tables`（只含指纹对不上的表，整表；`bookings` 多两个字段 `start_local` / `end_local`）。不是成员时返回 `trip_error: 'not_member'`，不给数据 |
| `wx_bridge_trips` | `p_key text, p_openid_hash text` | jsonb | 只有 `anon` | 只返回 `me`、`server_now`、`trips` |

- **认人**：`private.wx_bridge_keys` 存桥接密钥的 sha256（明文只在云函数的环境变量里）；`private.wx_bridge_users` 存 sha256(微信 openid) → `auth.users.id`。两张表在 `private` schema（PostgREST 不暴露），开了 RLS 但不建策略，只有 `postgres` 读得到；给某行写 `revoked_at` 就立刻吊销。认人失败一律报「未授权」（42501），不区分是密钥错还是 openid 错。
- **改动只有固定 9 种**：`expense.put`（记 / 改一笔，改时可带 `base_updated_at`，对方在这之后改过就报 40001）、`expense.delete`、`expense.restore`、`todo.set`、`todo.add`、`todo.delete`、`item.status`（完成 / 跳过 / 实际时间和情况）、`journal.put`（每天每人一篇，过期就合并正文）、`review.put`。
  - `todo.set`：勾 / 取消勾、数量，以及（20261014090000 起）`title`、`note`、`due_at`、`list`、`category`、`assignee_user_id`、`day_id`、`booking_id`、`item_id`，只改带了的字段；换了清单排到那个清单最后；可带 `base_updated_at`（和 `expense.put` 一样：改完和现在一样直接算成功，不一样且对方在这之后改过就报 40001）。只勾 / 取消勾时小程序不带 `base_updated_at`，后写的算数。
  - `todo.delete`（20261014090000 起）：`{id}`，可带 `base_updated_at`。`todos` 没有 `deleted_at`，所以是硬删除（网页端收到实时推送的 DELETE）；删掉了返回 `{ok, gone: true, deleted: true}`，已经不在了返回 `{ok, gone: true}`。
  - `todo.add`：新建；也用来**撤销删除**——带上删掉前的整行（同一个 `id`，外加 `assignee_user_id`、`done`、`done_by`、`done_at`、`sort`、`extra`、`created_at`）原样加回来，`created_by` 由触发器记成点撤销的人。带 `restore: true` 时，关联的天 / 预订 / 条目、负责人、勾的人已经不在了就置空，不让撤销失败。备注不再截到 500 字（超过 5000 字报错）。
  - 每种都走 `is_trip_member` / `is_trip_editor`（和 RLS 同一组函数）：账目、待办、条目要 owner/editor；日记、评级任何成员只能写自己的。付款人、分摊里的人、待办的负责人、关联的条目 / 预订 / 天 / 地点都必须属于这个行程。`tg_touch` / `tg_todos_done` 触发器照常记 `created_by` / `updated_by` / `done_by`，网页端的实时推送也照常收到。
- **边界**：`authenticated` 调不了这两个函数（它走正常的 RLS 路径）；`anon` 仍然没有任何表权限，也调不了 `private.*`。重发同一条改动不会重复写（新建按 id `ON CONFLICT`，更新前先比对、没变就不写）。`expense.put` 先算出改完的样子：和现在一样（重发、或上次其实已经写进去只是回包丢了）直接算成功，不同时才按 `base_updated_at` 查冲突。报错一律是中文（不认识的错误码写成「行程服务出错了（错误码）」；数据库的格式错误即使引用了用户填的中文，也换成「数据格式不对」「日期或时间的格式不对」，不漏英文原文）。
- **小程序的记账镜像**：小程序会把每趟的账目镜像成「豆豆小账本」里的记录（分类「旅行」、细分是行程短名，可用 `trips.extra.short_name` 指定）。默认只镜像 2026-10-01 以后结束的行程；`trips.extra.ledger_mirror` 写 `true` / `false` 可以单独打开、关掉某一趟。这两个键网站不用读，只是别删。
- **电脑端兜底**：`private.wx_bridge_apply_ops(p_uid, p_trip_id, p_ops)` 供 Mac 以 `postgres` 身份（Management API）代某个成员回写排队的改动，同样记对人；它不对外授权。
- 密钥和映射的插入语句（只贴哈希值）见迁移文件末尾的注释；云函数那一侧的部署步骤在小程序项目（不在这个仓库里）的 `cloudfunctions/trip/README.md`。

## A5. 文件存储

- 桶 `trip-files`：私有，单个文件上限 20 MB，允许 `image/jpeg`、`image/png`、`image/webp`、`image/gif`、`image/heic`、`image/heif`、`application/pdf`。
- 旧桶 `trip-photos` 已改成私有（当时是空的），规则和 `trip-files` 相同；新代码不要再用它。
- 路径规则：`{trip_id}/{user_id}/{用途}/{文件名}`。第一级必须是你所在行程的 id，第二级必须是你自己的 user id；成员能读本行程目录下所有人的文件，但只能在自己的目录里上传、覆盖、删除。
- 用途目录约定：`journal/`（日记照片）、`reviews/`（评级照片）、`bookings/`（确认单）、`receipts/`（小票）、`covers/`（封面）。文件名用随机 uuid 加扩展名。
- 数据库里只存路径（如 `demo2026/<uid>/journal/<uuid>.jpg`），不存 URL。显示时用 `createSignedUrl` / `createSignedUrls` 生成临时链接（建议 1 小时）。
- 照片上传前在浏览器压缩：长边约 2048px 的 JPEG；HEIC 先转码。

```js
const path = `${tripId}/${user.id}/journal/${crypto.randomUUID()}.jpg`;
await supabase.storage.from('trip-files').upload(path, blob, { contentType: 'image/jpeg' });
const { data } = await supabase.storage.from('trip-files').createSignedUrl(path, 3600);
```

## A6. 实时协作

- `supabase_realtime` publication 里有：`trips`、`trip_members`、`segments`、`places`、`bookings`、`days`、`items`、`contacts`、`todos`、`journal_entries`、`reviews`、`tips`、`expenses`。推送同样受 RLS 约束，只有成员收得到。
- 订阅：进入一个行程时建一个频道，每张表一个 `postgres_changes` 监听，带 `filter: trip_id=eq.<行程id>`；切换行程时退订再重建。
- 收到 INSERT/UPDATE：按 `id` 替换本地那一行（整行替换，不做字段合并）。
- 收到 DELETE：这类表启用了 RLS，DELETE 事件只带主键，按 `trip_id` 的过滤对它不起作用。前端按 `id` 在本地删除即可（id 全局唯一）。`items`、`expenses` 用软删除，走的是 UPDATE 事件。
- 冲突：按行后写者胜。编辑表单保存时只提交改动的字段（`update().eq('id', …)`），减少覆盖对方同时改的其他字段。

```js
supabase.channel(`trip:${tripId}`)
  .on('postgres_changes', { event: '*', schema: 'public', table: 'items', filter: `trip_id=eq.${tripId}` }, onChange)
  .subscribe();
```

## A7. 这次迁移的取舍

1. **新表名 `days` / `items`，旧的 `trip_days` / `trip_items` 确认 0 行后删除**，而不是同名重建。理由：
   - 线上旧前端还在读写 `trip_days`/`trip_items`（字段是 `day_date`、`planned_time`、`category`……）。同名重建后，旧前端要么报些莫名其妙的错，要么把残缺的行写进新表；换新名后旧代码只会干净地报“表不存在”，污染不了新数据。
   - 同名时 `CREATE TABLE IF NOT EXISTS` 会在旧表还在时静默跳过，得到的是旧结构；新名字让“重复执行”没有歧义。
   - 两张旧表只要有任何一行数据就都不删，给出提示。
2. **保留 `trips` 的 text 主键**：现有行 `taiwan2026` 和它关联的成员、记账、覆盖层都不用动；新行程 id 也用好记的 text。内容表的主键用 uuid。
3. **owner 的认定**：不把台湾创建者的 `editor` 改成 `owner`（旧前端只认 `editor` 可编辑，改了会变成只读），而是让 `trips.owner_id` 指向的成员同样算 owner。新行程由 `create_trip()` 直接写 `owner`。
4. **组合外键 `(trip_id, xxx_id)`**：防止一个行程的条目引用另一个行程的天、地点、预订。用到 Postgres 15 的 `ON DELETE SET NULL (列名)`，只置空引用列，不动 `trip_id`。
5. **记账的旧数据不动**：`currency` 仍是旧值（`NTD`/`RMB`/`HKD`），新加的生成列 `currency_iso` 自动换算成 ISO（`TWD`/`CNY`）；新数据直接写 ISO。旧列 `day_id`（text，'d1'…）、`amount_hkd`、`paid_by`、`split_with`、`receipt_url` 只给旧数据用。新数据用 `date` 对应到哪一天。
6. **邀请码只存哈希**，明文只在 `create_invite()` 返回时出现一次；加了次数上限和撤销。
7. **策略整表重建**：本文件管理的表，执行时先删掉表上全部策略（不管叫什么），再按文件重建。宽松策略之间是“或”的关系，面板里手动加过的任何一条残留都会让收紧失效。`storage.objects` 只删涉及 `trip-files`/`trip-photos` 的策略，不动其他桶。
8. **anon 撤销全部表权限**：在 RLS 之外再加一道。副作用：保活任务 `.github/workflows/keep-supabase-alive.yml` 匿名请求 `rest/v1/trips` 会从“200 空数组”变成 401（该任务只把 000 和 5xx 当失败，所以不会报错，但检查失去意义）。建议改为请求 `POST rest/v1/rpc/ping`，并把非 2xx 都当失败。
9. **去掉 `trip_id` 的默认值 `'taiwan2026'`**（`expenses`、`trip_invites`、`trip_user_state`、`checkins`），避免别的行程漏传 `trip_id` 时悄悄记到台湾下面。旧前端写入时都显式传了 `trip_id`，不受影响。
10. **删掉 `is_trip_empty()`**：只有“第一个用户自举成员”策略用它，而且它会暴露某个行程 id 是否存在。

执行后旧前端（现在的 GitHub Pages）受到的影响：台湾行程的查看、勾选、备注、记账对已有成员照常可用；生成邀请、用邀请加入、自动加入台湾行程、新建行程、“动态行程”模式会失败；匿名用户看不到打卡；旧照片的公开链接失效（桶当时是空的）。建议同时在 Supabase 的 Auth 设置里关闭公开注册，或只放行两个人的邮箱。

# B. 行程 JSON 文件格式

整理行程内容时照这一部分写。字段名和数据库列名完全一致。

## B1. 文件放哪

- 每个行程一个 JSON 文件，UTF-8，放在仓库外：`/Users/jeremy_k/Downloads/For Code/codex/Tourism/Taiwan/网站/行程数据/`，例如 `行程数据/<行程id>.json`。

- 照片、确认单 PDF 不放进 JSON，前端上传到存储桶后，JSON 或数据库里只记路径。

## B2. 顶层结构

```jsonc
{
  "trip":            { ... },   // 必填，一个对象（B4.1）
  "members":         [ ... ],   // 可选，成员（B4.2）。新行程至少写一个 owner，否则登录后谁都看不到
  "segments":        [ ... ],   // 以下都是可选数组，可以省略或写 []
  "places":          [ ... ],
  "bookings":        [ ... ],
  "days":            [ ... ],
  "items":           [ ... ],
  "contacts":        [ ... ],
  "todos":           [ ... ],
  "tips":            [ ... ],
  "expenses":        [ ... ],   // 可选：一般不在 JSON 里写，行程中在 App 里记
  "journal_entries": [ ... ],   // 可选：迁移旧日记时用
  "reviews":         [ ... ]    // 可选：迁移旧评级时用
}
```

数组之间的先后不重要，导入脚本按外键顺序写入。同一个数组内的先后会被用来自动编排序号（见各表的 `sort` / `sort_key`）。

## B3. 通用规则

### B3.1 id 与 key

- 除 `trip` 外，每一行都必须有 `id`。`id` 写一个人能读懂的 **key**，导入时脚本把它换成 uuid：

  ```
  uuid = uuidv5(命名空间, "<trip_id>:<key>")
  命名空间 = 957721cc-f32b-40b9-9d10-9094b1778228
  ```

  例：行程 `demo2026` 的 `item:d1-0930` → `dcf36b1e-fe25-5c9e-9524-0e0b107ec0d0`。同一个 key 永远得到同一个 uuid，所以重复导入是幂等的：已有的行被更新，不会重复新建。
- key 的格式：`<前缀>:<名字>`，名字只用小写字母、数字、`.`、`_`、`-`，以字母或数字开头，最长 80 位。前缀必须和所在数组对应：

  | 数组 | 前缀 | 名字约定 | 例子 |
  |---|---|---|---|
  | `segments` | `segment:` | 地名英文/拼音短名 | `segment:island` |
  | `places` | `place:` | 地点英文/拼音短名 | `place:airport`、`place:hotel-a` |
  | `bookings` | `booking:` | 类型-简称 | `booking:flight-out`、`booking:flight-back`、`booking:hotel-a` |
  | `days` | `day:` | `d` + 第几天（从 1 开始） | `day:d1` |
  | `items` | `item:` | `d<第几天>-<HHMM>`；同一时间多条加 `-b`、`-c`；没有确切时间用 `d<第几天>-<短名>`；备选池用 `pool-<短名>` | `item:d3-1500`、`item:d1-dinner-rain`、`item:pool-cable-car` |
  | `contacts` | `contact:` | 简称 | `contact:hotel-a-desk` |
  | `todos` | `todo:` | `<list>-<简称>` | `todo:confirm-hotel-b`、`todo:packing-passport` |
  | `tips` | `tip:` | `<kind>-<简称>` | `tip:warning-taxi` |
  | `journal_entries` | `journal:` | `d<第几天>-<成员ref>` | `journal:d1-jeremy` |
  | `reviews` | `review:` | `<地点短名>-<成员ref>` | `review:night-market-cathy` |
  | `expenses` | `expense:` | `d<第几天>-<简称>` | `expense:d1-grab` |

- **key 一旦导入就不要改。** 改了 key 等于新建一行，旧的那行还留在库里（脚本不删除任何行）。日期调整时也保留 `day:d1` 这类 key，只改 `date`。
- 也可以直接写现成的 uuid（例如引用 App 里新建的行），脚本原样使用。
- `trip.id` 不是 key，是行程 id 本身（如 `demo2026`），原样写入。
- 前端在 App 里新建的行用随机 uuid，没有 key，导入脚本不会碰它们。
- 台湾数据迁移时：条目的 key 用旧 id 加前缀（旧 `d3-1500` → `item:d3-1500`），同时写 `legacy_id: "d3-1500"`。

### B3.2 引用别的行

所有以 `_id` 结尾、指向别的表的字段（`day_id`、`place_id`、`booking_id`、`segment_id`、`item_id`、`parent_item_id`、`stay_booking_id`）写对方的 key，例如 `"place_id": "place:hotel-a"`。前缀必须对得上，被引用的 key 必须在同一个文件里定义，否则脚本报错。

JSON 字段内部（`details`、`stops`、`route_plan` 等）里名字以 `_id` 结尾、值是 key 的属性也会被换成 uuid，例如 `details.to_place_id`、`route_plan.stops[].place_id`。

### B3.3 引用成员

指向用户的字段（`owner_id`、`paid_by_user_id`、`assignee_user_id`、`done_by`、`user_id`、`created_by`）写 `"@<成员ref>"`，例如 `"@jeremy"`，ref 在 `members` 里定义。导入时按成员邮箱找到已注册用户的 uuid 替换。

- 对方还没注册：这个成员被跳过，所有 `"@ref"` 写成 `null`，脚本最后会列出来。对方注册后再导入一次即可补上。
- JSON 字段内部（如 `expenses.split.user_ids`、`details.baggage.addons[].paid_by_user_id`）里，整个字符串正好等于 `"@ref"` 的值也会被替换。

### B3.4 写、不写、写 null

- 写了的字段：新建时写入；已有的行被覆盖成 JSON 里的值。
- 没写的字段：新建时用数据库默认值；已有的行**保持数据库里现在的值**（包括在 App 里改过的，例如行程中勾成 `done` 的 `status`）。
- 写 `null`：清空这个字段。标了“不能为 null”的字段不能写 `null`，不想写就整个省略。
- 内容完全没变的行不会被更新。
- 例外：排序字段（`segments`/`bookings`/`contacts`/`todos`/`tips` 的 `sort`，`items` 的 `sort_key`）不写时，脚本按数组顺序自动生成，等于每次导入都写了它。在 App 里拖动过顺序又不想被重置，就用 `--only-new`。
- 不能写的字段：`created_at`、`updated_at`、`updated_by`（触发器维护）、`expenses.currency_iso`（自动计算）。`trip_id` 可以不写（脚本自动填），写了必须等于 `trip.id`。
- 想“只补新行、不覆盖任何已有行”（例如行程中 App 里已经改了很多），导入时加 `--only-new`。

## B5. JSON 字段的内部结构

用 TypeScript 写法描述：`?` 表示可选；`key` 指 B3.1 的 key（也可以是 uuid）；`user` 指 `"@ref"` 或 uuid。

### B5.1 公用结构

```ts
type Money = { amount: number; currency: string };          // currency 为 ISO 代码

type Link = {
  label: string;                                             // 按钮文字，如 "Google 地图"、"菜单"
  url: string;
  kind?: "maps" | "booking" | "menu" | "guide" | "social" | "video" | "other";
};

type Photo = {
  path: string;                                              // trip-files 里的路径
  caption?: string;
  taken_at?: string;                                         // tstz
  width?: number;
  height?: number;
};

type Attachment = {
  path: string;                                              // trip-files 里的路径
  name: string;                                              // 显示名，如 "确认单.pdf"
  mime?: string;                                             // 如 "application/pdf"
  size?: number;                                             // 字节
};
```

### B5.2 trips.cover

```ts
type Cover = {
  emoji?: string;          // "🏝️"
  accent?: string;         // 主题色 "#0EA5A4"
  accent_2?: string;       // 渐变第二色
  image_path?: string;     // 封面图在 trip-files 里的路径（{trip_id}/{user_id}/covers/…）
};
```

### B5.3 days.route_plan（当天的路线规划卡）

```ts
type RoutePlan = {
  title: string;                                   // "西线电动车环游"
  subtitle?: string;                               // "日和湾居出发，压缩成约 3 小时骑行"
  mode?: TransportMode;                            // 主要交通方式，取值见 B5.5
  metrics?: { label: string; value: string }[];    // [{ "label": "总距离", "value": "31 km" }]
  maps_url?: string;                               // Google 路线链接
  button_label?: string;                           // 按钮文字，默认 "打开路线"
  stops?: {                                        // 路线经过的点，按顺序
    name: string;
    note?: string;                                 // "补给 / 短停"
    place_id?: key;                                // 有对应地点时写，坐标从地点读
    lat?: number;                                  // 没有地点时可直接写坐标
    lng?: number;
  }[];
};
```

### B5.5 items.transport_in（怎么到这一站）

```ts
type TransportMode =
  | "walk" | "metro" | "bus" | "taxi" | "grab" | "scooter" | "bicycle"
  | "ferry" | "train" | "hsr" | "flight" | "car" | "cable_car" | "other";

type TransportOption = {
  mode: TransportMode;
  label?: string;              // "推荐"、"省钱版"
  duration_min?: number;       // 分钟
  distance_km?: number;
  cost?: {                     // 费用
    amount: number;
    amount_max?: number;       // 有区间时写上限
    currency: string;
    per?: "person" | "total";  // 默认 total
  };
  recommended?: boolean;       // 推荐方案，最多一个 true
  note?: string;               // "机场出口排队，Grab 上车点在 B 门"
  maps_url?: string;           // 这一段的 Google 路线
};

type TransportIn = {

```

### B5.6 items.cost_estimate（费用估算）

```ts
type CostEstimate = {
  amount: number;              // 估算金额（有区间时是下限）
  amount_max?: number;         // 区间上限
  currency: string;            // ISO 代码
  per?: "person" | "total";    // 每人还是总价，默认 total
  note?: string;               // "人均，含饮料"
};
```

预算汇总：`per: "person"` 的乘以同行人数（`trip.extra.party_size`，没有则按 owner/editor 成员数）；有 `amount_max` 时分别汇总下限和上限；换算成 `home_currency` 后相加。

## B7. 导入命令

在仓库目录下运行（Node 18 及以上）：

```bash
# 1. 只校验，打印每张表将写入几行；不读钥匙串、不连网
node tools/seed-trip.mjs "../行程数据/<行程id>.json" --dry-run

# 同时列出每个 key 对应的 uuid（排查问题用）
node tools/seed-trip.mjs "../行程数据/<行程id>.json" --dry-run --ids

# 2. 正式导入：会先显示汇总，输入 yes 才写入
node tools/seed-trip.mjs "../行程数据/<行程id>.json"

# 行程已经开始、App 里改过很多：只补新行，不覆盖已有行
node tools/seed-trip.mjs "../行程数据/<行程id>.json" --only-new
```

- 正式导入需要先在终端运行过 `supabase login`（访问令牌存在 macOS 钥匙串里，脚本运行时读取，不打印、不写文件）。
- 整个导入是一条 SQL 语句、一个事务：任何一行出错，数据库一行都不改。
- 脚本只新增和更新，不删除任何行。要删除，在 App 里删，或者手动处理。
- `--print-sql` 会把含行程内容的 SQL 打到屏幕上，只在排查问题时用，不要贴到公开的地方。
